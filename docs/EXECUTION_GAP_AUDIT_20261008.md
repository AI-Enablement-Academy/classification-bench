## Confirmed findings

The completion verdict is **REQUEST-CHANGES** because required execution features remain absent. These findings describe reachable operator failures or missing required features, not evidence of actual excess spending. Severity follows the [canonical rubric](../../scripts/lib/codex-review-rubric.md).

1. BLOCKING: no enforced aggregate experiment cap. Separate valid child scopes can each reserve their entire cap; no allocation relation constrains their sum. The requested smoke/full/aggregate budget feature therefore fails for ordinary multi-scope operation. [Current scope creation](../classification_bench/budget.py) and [budget contract](BUDGET_API.md) enforce each scope independently and warn against multiplying one authorization manually.
2. BLOCKING: expired subscription guards cannot be renewed for a paused run. A normal run paused beyond 24 hours fails preflight. Updating `extra_usage_verified_at` changes plan/run identity, and an otherwise correctly rewritten grant fails with `benchmark configuration changed for this database`. The offline repro paused after one of two requests, renewed the timestamp, attempted resume and retained exactly one dispatch. [Adapter freshness check](../classification_bench/subscription_adapters.py), [immutable run binding](../classification_bench/benchmark.py) and [documented limitation](SUBSCRIPTION_RUNNER.md) confirm the failure.
3. BLOCKING: one experiment cannot include USD and REQ routes. `preview` rejects a matrix containing OpenRouter and Codex with `different accounting units require separate run scopes`. This fail-closed behavior preserves accounting units, but the required unified multi-route workflow still fails. [Runner loading](../classification_bench/benchmark.py) and [unit tests](../tests/test_request_accounting.py) identify the boundary.
4. BLOCKING: supported OpenRouter reasoning/effort cannot be expressed. The adapter rejects every reasoning setting before checking endpoint support. Its accepted controls are limited to temperature, top-p and maximum output tokens; the required experimental reasoning feature is missing. The offline fixture adding `"reasoning": {"effort": "medium"}` raises `unsupported OpenRouter setting`. [Adapter validation](../classification_bench/adapters.py) is the source.
5. BLOCKING: catalog discovery requires already-known IDs. The `catalog` command requires both `model` and `provider` and fetches that pinned endpoint. It cannot list available models or providers for operator selection, so E2 discovery is incomplete. [CLI](../classification_bench/cli.py) and [endpoint snapshot function](../classification_bench/adapters.py) confirm the supported operation.
6. RESIDUAL: family, purpose and training-lineage metadata are incomplete. The frozen configuration permits `model_type`, but lacks separate declaration/evidence fields for E11. Reports currently show unknown metadata honestly; no false lineage claim or dispatch failure was confirmed. This remains a requested completion item. [Configuration validation](../classification_bench/core.py) and [parity row E11](FEATURE_PARITY.md) define the gap.
7. RESIDUAL: historical status prose can read as current guidance. The README headline still names 338 tests; older status paragraphs list report features now implemented. The matrix identifies its baseline rows as historical, but a final row-by-row overlay should replace ambiguous completion guidance. This affects handoff accuracy and does not invalidate the passing checks. [README](../README.md), [implementation history](IMPLEMENTATION_STATUS.md) and [parity matrix](FEATURE_PARITY.md) are the sources.

The privacy correction independently receives **APPROVE**, with no remaining finding: [three regression tests](../tests/test_cli_privacy.py) verify actual plan/evaluate output permissions, both export paths, no overwrite/symlink following and unchanged stdout JSON. Prior outputs are preserved rather than silently rewritten.

## Next implementation: one authoritative accounting database

Implement the ledger layer first, then integrate plural run bindings and the operator bundle. [ExecutionLedger](../classification_bench/execution.py) already owns multiple budget scopes and commits reservation/dispatch intent or settlement in one SQLite transaction. Keeping parent allocations and child execution in that database avoids an observed child overrun being committed before its parent learns of it.

The current benchmark layer permits one immutable run binding and one run-control row per database. Its global request key also needs a namespace: [plan construction](../classification_bench/core.py) hashes only the particular task/configuration/prompt/repeat/batch/items; the manual fixture's first smoke and full request IDs were identical. A new workflow can use `SHA256(run_sha256, logical_request_id)` as the storage key while retaining the original plan/provider request ID in manifests and exports. Preserve existing single-run databases and historical bytes; use an explicit new workflow version rather than relabeling them.

Proposed ledger API, subject to implementation review:

| Method | Required contract |
| --- | --- |
| `create_aggregate(scope, cap, currency, scale, authorization_source)` | Create explicit parent terms with private authoritative-database identity. No permission or unused budget is inferred from an old document. |
| `allocate_child(parent_scope, child_scope, allocation_id, cap, run_sha256, authorization_source)` | Atomically create a managed child and reserve its full cap. Parent/child units and scales must match. Allocation ID, child scope and bound run identity cannot be reused for a different child. Reject attaching an unrelated existing scope. |
| `increase_allocation(child_scope, amendment_id, expected_cap, new_cap, authorization_source)` | Atomically increase both allocation and child cap after checking parent capacity. A stale or conflicting amendment fails; an identical amendment is idempotent. Direct `increase_cap` on a managed child rejects bypass. |
| `increase_cap(parent_scope, ...)` | Preserve the existing explicit, conditional amendment contract for parent authority. Never increase automatically. |
| `aggregate_balances(parent_scope)` / `verify_aggregate(parent_scope)` | Show allocations, child known charges, active reservations, unknown holds, unused allocation capacity and freeze state separately; verify immutable allocation/amendment history. |

Use new aggregate-term, child-allocation and immutable allocation-event tables, with child scopes referencing the existing `scopes` table. Retain allocations monotonically, including failed child initialization; no automatic refunds. Parent accounted exposure is the sum of `max(allocated_child_cap, child_known + child_active + child_held)`, so observed charges are not added twice to their allocation.

Every managed child reservation must check parent freeze and allocation coverage inside the same `BEGIN IMMEDIATE` transaction as the existing reserve. Settlement must record the full charge and freeze the ancestor in that same transaction after any above-bound child charge, including an overrun that remains below the child's total cap. Cap increases, restart and recovery must not clear a committed freeze; already-admitted work may preserve its evidence.

Bind the authority database to an immutable database ID and canonical file location/identity. A normal copied database must not become an independent spending authority. A reviewed restore or relocation needs an explicit future contract; fail closed until then. USD and REQ parents remain separate components of an experiment budget vector, with no conversion or claim that request allocations bound subscription dollars.

Ledger acceptance should cover multiple children, concurrent real-process allocations/reservations/amendments, duplicate/conflicting allocation identities, copied authority databases, unknown holds, an overrun in child A blocking child B, duplicate settlement, crash/restart and unchanged legacy behavior. Test a parent cap of 10 with child caps 4 and 6: both allocations fit, a further allocation fails, usage inside either cap does not free parent allocation, and an above-bound settlement freezes sibling admission even if total observed exposure is below 10. This is an interim ledger deliverable; mixed-unit scheduling, shared provider concurrency, phase selection and report composition remain integration work.

After that integration, move expiring account assertions into append-only guard revisions bound to the unchanged experimental configuration. Renewal must record an actual fresh account check, preserve every prior guard/evaluation/request identity and retain ambiguous holds and existing safety blocks. An expired assertion must continue to prevent dispatch; a cap amendment alone is insufficient.
